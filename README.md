# Asteria FlightStack + MissionOps

**A local spacecraft software laboratory: inject a fault, watch onboard protection respond, execute a guarded recovery, and reconstruct the incident.**

Two connected projects share one versioned interface and one interactive console. The flight process is real C++17 code; browser commands go through the Python ground gateway before reaching it. Telemetry is generated by a simplified synthetic spacecraft model, not mocked chart data.

**Release: 0.1 — functional independent prototype.** This release does **not** complete the full original F Prime / Open MCT master specification. See [scope and gaps](docs/scope-and-gaps.md). No flight qualification or mission heritage is claimed.

## Run in three commands

Requirements: Python 3.9+ and a C++17 compiler (`clang++` or `g++`). No Python packages, Node, API keys, cloud account, hardware purchase, or network downloads are needed when those tools are installed.

```sh
cd /path/to/asteria
python3 scripts/build.py
python3 ground/server.py
```

Open **http://127.0.0.1:8080** in a current Chrome, Firefox, Safari, or Edge browser. On macOS, double-click `run.command` as an alternative. If port 8080 is busy, use `python3 ground/server.py --port 8081` and open that port.

1. Initialize an **Administrator** training session with seed **42**.
2. Select **First light**, then execute the three commissioning steps.
3. Click **Run** and inspect the live payload and subsystem telemetry.
4. Open **FlightStack** and inject **Sensor stale**. Observe SAFE mode and payload shutdown.
5. Clear fault sources; advance 10 seconds; send `RECOVER`, then `RESUME`.
6. Open **Replay & debrief**, load recorded telemetry, scrub history, and export a mission journal.

The training role is fixed for each session. End a session to select another role. Roles demonstrate gateway authorization; they are not production account authentication. Up to eight sessions can run at once, each with its own flight process. Session access tokens stay in browser session storage and server memory. Restarting the server expires sessions, while journal records remain in `data/missions.sqlite3`.

## What you can experience

- **Mission overview:** live trends, illustrative orbit, subsystem health, alerts, four guided scenarios.
- **FlightStack:** four operating modes, six fault sources, recovery gates, 26-channel dictionary with six subsystem filters.
- **MissionOps:** 12 flight commands, two administrative simulator controls, ten ground rules, six executable procedures, acknowledgment and audit views.
- **Replay & debrief:** read-only recorded telemetry, JSON journal export, Markdown after-action reports, measured local command latency.
- **Engineering:** architecture, flight rule baseline, and fidelity boundaries.

No fonts, telemetry, analytics, scripts, or other assets are fetched from external services. The application binds only to loopback. **Do not expose this training server to the Internet.** Public hosting requires a separate reviewed deployment design; a static host cannot run its C++/Python backend.

## Verify

```sh
python3 scripts/verify.py
python3 scripts/build.py --sanitize
python3 scripts/sanitize.py
python3 scripts/benchmark.py
# With the server running in another terminal:
python3 scripts/http_smoke.py
```

Reports are written to `evidence/`. Test counts come from unittest, not a design target. The benchmark stores raw latency samples and a 30-minute scenario trace. See [technical report](docs/technical-report.md) for the exact verified scope and limitations.

## Engineering decisions

The dependency-free core makes the prototype reproducible on a zero-dollar local setup. It deliberately uses a custom C++ component model, synchronous local process transport, Python's standard HTTP server, and SQLite. **It does not implement F Prime, Open MCT, FastAPI, PostgreSQL, WebSockets, physical HIL, RTOS scheduling, or CCSDS.** Those are explicitly open master-spec work items, not implied accomplishments.

Shared telemetry and commands are counted once across both projects. See [requirements](docs/requirements.csv), [interface control](docs/interface-control.md), [demo walkthrough](docs/demo-script.md), and [manual GitHub publication](docs/github-manual.md).
